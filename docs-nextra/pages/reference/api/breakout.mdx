# Breakout API

Le breakout copie les cas d'un dictionnaire CSWeb dans une base relationnelle
(PostgreSQL, MySQL ou SQL Server), une table par niveau et par enregistrement.
Cette page dit comment une application externe (plateforme, script, BI) le
configure, le déclenche et le suit.

<div className="nx-mt-4" />

> **Pas de compte CSWeb ni d'OAuth.** Le breakout se pilote par des webhooks à
> jeton (`Authorization: Bearer <jeton>`), un jeton par webhook depuis
> 8.0.14 / 8.1.20. Il n'existe pas d'endpoint `/api/breakout/...` dans l'API
> REST de CSWeb.

## Vue d'ensemble

| Besoin | Comment | Jeton |
|---|---|---|
| Configurer la base cible d'un dictionnaire | Interface **Data Settings** (recommandé), ou `POST /dictionary-schema-webhook.php` | `WEBHOOK_TOKEN_SCHEMA` |
| Planifier (toutes les N minutes) | Interface **Breakout Scheduler** | — |
| Déclencher à la demande | `POST /breakout-webhook.php` | `WEBHOOK_TOKEN_BREAKOUT` |
| Suivre : cas collectés, traités, en attente, dernier et prochain passage | `GET /breakout-status-webhook.php` | `WEBHOOK_TOKEN_STATUS` |
| Lire les journaux d'un passage | `GET /log-reader-webhook.php` | `WEBHOOK_TOKEN_LOGS` |
| Lire les médias (audio, photos) | `POST /media-webhook.php` | `WEBHOOK_TOKEN_MEDIA` |

Les variables, les codes d'erreur et la limite de débit sont décrits dans le
[guide Webhooks](/guides/admin/webhooks).

## 1. Configurer la base cible

Dans CSWeb : **Data Settings → Add**, choisir le dictionnaire, puis le type de
base (PostgreSQL, MySQL…), l'hôte, le port, la base, l'utilisateur et le mot de
passe. Plusieurs dictionnaires peuvent être ajoutés d'un coup vers la même base.
Détails : [Breakout sélectif](/guides/breakout/selective).

Le webhook `dictionary-schema-webhook.php` sait enregistrer une cible
(`action: register` avec `host_name`, `schema_name`, `schema_user_name`,
`schema_password`), mais il ne prend ni le type de base ni le port : pour une
cible PostgreSQL ou un port non standard, utilisez **Data Settings**.

```bash
# Lire la configuration de tous les dictionnaires
curl -H "Authorization: Bearer $WEBHOOK_TOKEN_SCHEMA" \
  "https://csweb.example.org/dictionary-schema-webhook.php?action=list"
```

## 2. Planifier

Dans CSWeb : **Breakout Scheduler**, une expression cron par dictionnaire
(par exemple `*/15 * * * *` pour toutes les 15 minutes). Le planificateur tourne
chaque minute dans le conteneur. Détails : [Breakout planifié](/guides/breakout/scheduled).

## 3. Déclencher à la demande

```bash
curl -X POST "https://csweb.example.org/breakout-webhook.php" \
  -H "Authorization: Bearer $WEBHOOK_TOKEN_BREAKOUT" \
  -H "Content-Type: application/json" \
  -d '{"dictionary": "PRAPS2_ENTRETIEN"}'
```

L'appel attend la fin du passage (5 minutes au plus) et renvoie :

```json
{
  "success": true,
  "data": {
    "dictionary": "PRAPS2_ENTRETIEN",
    "exitCode": 0,
    "durationMs": 4210,
    "logFile": "PRAPS2_ENTRETIEN_20261125_103000-api.log",
    "output": "…"
  },
  "error": null
}
```

Un passage en échec répond `500 breakout_failed` avec le code de sortie.

## 4. Suivre

```bash
curl -H "Authorization: Bearer $WEBHOOK_TOKEN_STATUS" \
  "https://csweb.example.org/breakout-status-webhook.php?dictionary=PRAPS2_ENTRETIEN"
```

La réponse donne, par dictionnaire : base cible configurée ou non, planning,
cas collectés, cas traités, cas en attente, taux, `is_up_to_date`, dernier et
prochain passage. Référence complète : [Breakout Status Webhook](/reference/api/breakout-status).

Pour les journaux d'un passage :

```bash
curl -H "Authorization: Bearer $WEBHOOK_TOKEN_LOGS" \
  "https://csweb.example.org/log-reader-webhook.php?file=PRAPS2_ENTRETIEN_20261125_103000-api.log&lines=200"
```

## 5. Tables produites

Le breakout crée dans la base cible une table par niveau et par enregistrement
du dictionnaire, préfixée par le nom du dictionnaire en minuscules, sans le
suffixe `_DICT` (par exemple
`praps2_entretien_level-1`, puis les tables des enregistrements), ainsi que
`praps2_entretien_cases` et `praps2_entretien_cspro_jobs` (suivi des passages).

Les noms suivent le dictionnaire : ils ne changent que si le dictionnaire
change (ajout, renommage ou suppression d'enregistrements ou de variables).
Toute modification du dictionnaire doit donc être annoncée aux applications qui
lisent ces tables.
