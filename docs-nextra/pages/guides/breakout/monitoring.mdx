# Monitoring Breakout

Surveiller et diagnostiquer les jobs de breakout en temps réel.

## Monitoring via l'Interface Web

### Breakout Health (tableau de bord)

Menu **Breakout Health** : l'état de chaque dictionnaire en un écran, pensé pour
suivre une enquête avec beaucoup de dictionnaires. Les colonnes Total cases et
Processed arrivent en 8.0.8 / 8.1.14 ; le statut « Schedule overdue » et le filtre
« Hide empty » en 8.0.9 / 8.1.15 ; les compteurs calculés en arrière-plan en
8.0.11 / 8.1.17 ; les chiffres exacts dans les cartes en 8.0.12 / 8.1.18.

**Cartes du haut** : dictionnaires configurés, cas collectés (CSWeb), cas traités
(base de breakout), taux global, cas en attente, erreurs. Avec un filtre actif,
elles portent sur les dictionnaires filtrés.

Les nombres sont exacts jusqu'à 999 999 (`3,798` et `3,772`, avec l'écart de 26
visible dans Pending) ; au-delà, ils s'affichent en millions avec deux décimales
(`2.91M`) et le chiffre exact apparaît au survol. Avant 8.0.12 / 8.1.18, les
cartes arrondissaient à une décimale : 3 798 et 3 772 s'affichaient tous deux
« 3.8K ».

**Colonnes du tableau**

| Colonne | Contenu |
|---|---|
| Total cases | Cas présents dans CSWeb pour ce dictionnaire (nombre exact) |
| Processed | Cas écrits dans la base de breakout. En orange s'il est inférieur au total ; « — » si le comptage est impossible (non configuré, cible injoignable : la raison s'affiche au survol) |
| Completion | Processed / Total cases |
| Pending | Cas restant à traiter (nombre exact) |
| Last run / Next run | Dernier passage, prochain passage. « off » : pas de planning actif. « late 2h » : planning en retard |
| Exit | Code de sortie du dernier passage (0 = succès) |

**Statuts** (pastille de couleur et filtre « All statuses »)

| Statut | Signification | Action |
|---|---|---|
| Up-to-date | Tous les cas sont traités | — |
| Pending | Des cas restent à traiter | Attendre le prochain passage ou **Run now** |
| Schedule overdue | Le planning est actif mais son passage prévu date de plus de 15 min : le planificateur ne tourne pas | Vérifier le conteneur (`docker compose ps`) et `var/logs/scheduler-cron.log` |
| Target unreachable | La base de breakout ne répond pas (pare-feu, hôte, port, mot de passe) | Lire la cause affichée sous le nom du dictionnaire |
| Error | Le dernier passage a échoué | Ouvrir le journal (icône à droite) |
| Never run | Configuré mais jamais lancé | **Run now** ou activer le planning |
| Not configured | Pas de breakout pour ce dictionnaire | Settings → Data → Add Configuration |

**Filtres** : statut, planning (Cron enabled / disabled), recherche par nom, et
**Hide empty** (coché par défaut, mémorisé par navigateur) qui masque les
dictionnaires sans aucun cas ni breakout : menus, listes de référence, écrans de
connexion.

Une base de breakout injoignable ne bloque jamais la page : la connexion est
coupée après 3 s et le résultat gardé 60 s. **Refresh** refait le test aussitôt.

#### Compteurs calculés en arrière-plan (8.0.11 / 8.1.17)

Compter les cas de chaque dictionnaire, dans CSWeb et dans la base de breakout,
est la seule opération coûteuse de la page. Depuis 8.0.11 / 8.1.17, ce comptage
se fait en arrière-plan et la page ne fait que lire le résultat : elle s'ouvre
instantanément, quel que soit le nombre de dictionnaires.

| 100 dictionnaires, 2,9 millions de cas | Avant | 8.0.11 / 8.1.17 |
|---|---|---|
| Ouverture de la page | 10 s | 0,01 s |
| Filtre (ex. « Pending ») | 11 s | 0,01 s |

Les compteurs sont recalculés :

- toutes les 2 minutes (tâche planifiée incluse dans l'image Docker) ;
- après chaque breakout planifié, pour le dictionnaire concerné ;
- au clic sur **Refresh** ;
- dès qu'un dictionnaire est ajouté ou que sa base de breakout est modifiée.

La barre d'outils indique leur âge (« Counts updated 1m ago ») et affiche
« Updating counts… » pendant un recalcul ; les chiffres se mettent à jour seuls
à la fin.

Les compteurs sont stockés dans la table `cspro_breakout_metrics`, créée
automatiquement : aucune étape de mise à jour n'est nécessaire.

**Hors Docker** (hébergement mutualisé), la tâche `csweb:scheduler-run` déjà
planifiée recalcule les compteurs quand ils ont plus de 3 minutes. Pour des
chiffres plus frais, ajoutez :

```bash
*/2 * * * * php /chemin/vers/csweb/bin/console csweb:breakout-metrics
```

Lancement manuel, par exemple pour vérifier le temps de calcul :

```bash
docker compose exec csweb php bin/console csweb:breakout-metrics -v
```

### Onglet Breakout Logs

La page **Settings > Data**, onglet **Breakout Logs** offre un monitoring complet :

- **Sidebar dictionnaires** : voir les logs par dictionnaire avec badge compteur, recherche instantanée
- **Table paginée** : tri par dictionnaire, date, taille, type (manual/scheduled)
- **Modal viewer** : visualisation du contenu (thème sombre VS Code, numéros de ligne, word wrap toggle, scroll to top/bottom)
- **Actions** : télécharger ou supprimer chaque fichier log avec confirmation

### Onglet Application Log

L'onglet **Application Log** permet de consulter le fichier `ui.log` de Symfony :

- Nombre de lignes, taille, date de modification
- Visualisation complète avec word wrap et copie vers le presse-papiers
- Suppression avec modal de confirmation

## Logs en Temps Réel (CLI)

### Tail Logs

```bash
# Logs Docker
docker compose logs -f csweb

# Logs breakout individuels
tail -f /var/www/html/var/logs/breakout/*.log
```

### Filtrer par Dictionnaire

```bash
# Grep pour dictionnaire spécifique
docker compose logs csweb | grep "EVAL_DICT"

# Grep erreurs
docker compose logs csweb | grep ERROR
```

## Progress Tracking

### Commande avec Verbose

```bash
php bin/console csweb:process-cases-by-dict EVAL_DICT -vvv
```

Output exemple :

```
[INFO] Processing dictionary: EVAL_DICT
[INFO] Running blob breakout process.
[INFO] Processing dictionary: EVAL_DICT- Running threads 0
[INFO] creating a new blob breakout thread
...
```

### Watch Progress

```bash
# Compter rows pendant breakout
watch -n 5 'docker compose exec postgres psql -U csweb_analytics -d csweb_analytics -c "SELECT COUNT(*) FROM eval_cases;"'
```

## Détection Erreurs

### Codes d'Erreur Courants

| Erreur | Cause | Solution |
|--------|-------|----------|
| `Connection refused` | DB non accessible | Vérifier docker compose ps |
| `Driver not found` | pdo_pgsql manquant | Installer driver |
| `Table already exists` | Breakout déjà fait | Utiliser --overwrite |
| `Out of memory` | Trop de cases | Augmenter memory_limit |

### Check Database Connection

```bash
php bin/console csweb:check-database-drivers
```

### Test Connection Avant Breakout

```bash
# PostgreSQL
docker compose exec postgres pg_isready

# MySQL
docker compose exec mysql-breakout mysqladmin ping

# SQL Server
docker compose exec sqlserver /opt/mssql-tools/bin/sqlcmd -S localhost -U sa -Q "SELECT 1"
```

## Alertes

### Email sur Erreur

Script wrapper :

```bash
#!/bin/bash
DICT=$1
LOG=$(mktemp)

php bin/console csweb:process-cases-by-dict $DICT > $LOG 2>&1

if [ $? -ne 0 ]; then
    mail -s "Breakout Failed: $DICT" admin@example.com < $LOG
fi

rm -f $LOG
```

### Slack Webhook

```bash
#!/bin/bash
SLACK_WEBHOOK="https://hooks.slack.com/services/YOUR/WEBHOOK"

curl -X POST -H 'Content-type: application/json' \
  --data '{"text":"❌ Breakout failed: Connection refused"}' \
  $SLACK_WEBHOOK
```

### Health Check Endpoint

Créer `health-check.php` :

```php
<?php
// Vérifier dernière exécution breakout
$lastRun = filemtime('/tmp/last-breakout.lock');
$now = time();
$diffHours = ($now - $lastRun) / 3600;

if ($diffHours > 24) {
    http_response_code(500);
    echo json_encode(['status' => 'error', 'message' => 'No breakout in 24h']);
} else {
    echo json_encode(['status' => 'ok', 'last_run_hours_ago' => $diffHours]);
}
```

Monitorer avec UptimeRobot ou similaire.

## Tableaux de Bord

### Requêtes SQL Monitoring

```sql
-- Nombre total de cases
SELECT COUNT(*) as total_cases FROM eval_cases;

-- Cases par jour
SELECT DATE(modified_date) as date, COUNT(*) as count
FROM eval_cases
GROUP BY DATE(modified_date)
ORDER BY date DESC
LIMIT 7;

-- Taille tables
SELECT
    table_name,
    pg_size_pretty(pg_total_relation_size(table_name::regclass)) as size
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY pg_total_relation_size(table_name::regclass) DESC;
```


### Vacuum PostgreSQL

```bash
docker compose exec postgres vacuumdb -U csweb_analytics -d csweb_analytics --analyze
```

### Optimize MySQL

```bash
docker compose exec mysql-breakout mysqlcheck -u breakout_user -p --optimize --all-databases
```

## Troubleshooting

### Breakout Bloqué

Si processus bloqué :

```bash
# Trouver PID
ps aux | grep process-cases

# Kill process
kill -9 <PID>

# Supprimer lock file
rm -f /tmp/breakout-*.lock
```

### Tables Corrompues

PostgreSQL :

```bash
docker compose exec postgres psql -U csweb_analytics -c "REINDEX DATABASE csweb_analytics;"
```

MySQL :

```bash
docker compose exec mysql-breakout mysqlcheck -u breakout_user -p --repair csweb_breakout
```
